## Part 1:業界標準——Preston Blair Phoneme Series

動畫業界對嘴形冇「一個音一個形狀」咁做,而係用一套精簡嘅標準集合:<cite index="207-1">專業做法唔會為每一個語音單獨整一個獨特嘅嘴形,而係依賴一套標準化嘅 8 至 12 個核心口型(viseme),呢個做法可以追溯到 Disney 嘅 12 個原型嘴形——一個口型往往代表多個語音,例如 M、B、P 就共用同一個閉嘴口型。</cite>

**術語**:<cite index="207-1">音素(phoneme)係聲音嘅單位;口型(viseme)係螢幕上代表呢啲聲音嘅嘴形。你聽到一個音素,你畫/駛動一個口型。</cite>

**核心邏輯**:<cite index="207-1">有啲聲音喺聽覺上唔同,但視覺上好相似——呢個係點解一張圖表會將佢哋歸埋一齊嘅原因。</cite>例如:<cite index="207-1">M、B、P 都需要閉嘴;F、PH 係下唇碰上排牙齒;O、U 嘴巴會圓起嚟變成相似嘅前伸口型;靜默/冇聲通常返去中性/休息嘴形。</cite>

呢個標準系統業界稱做 **Preston Blair Phoneme Series**,<cite index="55-1">只用 10 個口型就映射晒所有可能嘅音素,呢套系統喺卡通動畫嘅臉部動畫入面極之常用。</cite>

## Part 2:標準口型清單(對應你套點位系統)

| 口型代號 | 例字 | 嘴形描述 | 對應輕量版參數 | 對應專業版新增點位 |
|---|---|---|---|---|
| **AI**(A) | hi, time, father | 大幅張開,下顎明顯下墜 | mouthOpen: 0.75 · mouthWidth: 1.0 | JW-CTR 明顯下移 |
| **E** | way, get | 中度張開,嘴角微向後拉 | mouthOpen: 0.35 · mouthWidth: 1.15 | UL/LL 左右段拉闊 |
| **O** | go, boat | 中高張開,嘴形變圓 | mouthOpen: 0.5 · mouthWidth: 0.75 | UL-CTR/LL-CTR 前突感 |
| **U / WQ** | you, queen, wet | 小幅開合,嘟嘴前伸 | mouthOpen: 0.15 · mouthWidth: 0.6 | 同上,幅度更細 |
| **FV** | fish, very | 下唇貼上排牙齒(特殊形狀,非單純開合) | mouthOpen: 0.08(近似) | LL-CTR 向上貼近 UL-CTR |
| **L** | let, love | 中度張開,舌尖可見(本系統暫不含舌頭點位) | mouthOpen: 0.3 | 標記為近似值 |
| **MBP** | mom, bob, pop | 完全閉合 | mouthOpen: 0 | — |
| **一般輔音**(C,D,G,K,N,S,T,X,Y,Z) | — | 輕微開合嘅預設輔音口型 | mouthOpen: 0.1 · mouthWidth: 1.0 | — |
| **Rest**(靜默/中性) | — | 休息嘴形 | mouthOpen: 0.03 · mouthWidth: 1.0(同你之前嘅中性值一致) | — |

**重要限制備註**:FV 同 L 呢兩個口型嘅視覺特徵(下唇貼牙、舌尖外露)喺你而家嘅點位系統入面冇專屬點位可以精確表達,建議暫時用「開合幅度近似值」頂替,後續如果要做到專業級寫實嘴形,可以考慮加返「牙齒可見度」「舌尖點位」呢兩個新類別。

## Part 3:核心問題——口型同情緒點樣同時共存?

呢個係你套系統之前完全未處理過嘅缺口:嘴巴一方面要「講緊嘢」(口型),另一方面又要「帶住情緒」
(嘴角上揚/下垂)。如果處理得唔好,會出現機械人研究入面明確指出嘅衝突:

<cite index="61-1">如果將表情權重直接疊加落去,唔理speech production引起嘅臉部郁動,會產生唔自然嘅表情。例如將「驚訝」表情(令個口完全張開)同 /b/、/f/、/v/ 呢類需要閉嘴或者接近閉嘴發音嘅口型組合埋一齊,就會產生衝突;將「開心」情緒同 /o/ 呢類嘟嘴口型組合,都會令視覺語音同表情變得唔自然、顯得怪異或者唔正常。</cite>

### 3.1 解決方案:ExpressionBot 嘅混合公式(可直接採用)
一篇機械人臉部研究提出咗一條實用嘅混合公式:

```
F_i = F_c + λ_i × (F_i^max − F_0)
```

<cite index="61-1">當中 F_c 代表目前嘅口型,F_j^max 係目標情緒喺最大強度嘅表情模型,F_0 係中性模型,λ_j 係第 j 個表情模型嘅強度參數,範圍 0 至 1。</cite

**關鍵做法**:<cite index="61-1">為咗解決呢個問題,佢哋設計咗一張表,為每一個「口型-情緒」組合都提供一個口型權重同一個情緒最大權重,呢啲數值係逐一憑經驗調整出嚟。佢哋仲將表情嘅變形目標分成上下兩部分——上半臉包含由鼻尖以上嘅所有部分。</cite>

### 3.2 你套系統嘅具體實作規則

**規則一:上下臉分離**(呼應之前已有嘅點位分區)
- 眉毛、眼部、額頭、臉頰上部(CH-*-UP):**完全由情緒主導**,唔受口型影響
- 嘴部、下巴、臉頰下部:**由口型主導開合/寬度,情緒只做有限度嘅疊加**

**規則二:每個口型有獨立嘅「情緒容許權重」(emotionWeight)**

| 口型 | emotionWeight | 原因 |
|---|---|---|
| AI | 0.9 | 大張口,有充足空間疊加嘴角形狀 |
| E | 0.85 | 中度張口,空間尚算充足 |
| O | 0.5 | 圓形口型,情緒疊加太多會破壞「O」嘅可辨識度 |
| U/WQ | 0.35 | 嘟嘴口型,同開心/驚訝嘅衝突風險最高 |
| FV | 0.3 | 下唇貼牙嘅精確形狀,情緒疊加容易破壞可辨識度 |
| L | 0.6 | 中度開合,中等空間 |
| MBP | 0.25 | 完全閉合,情緒疊加空間最少(只可以透過嘴角微調,唔可以改變開合) |
| 一般輔音 | 0.7 | 輕微開合,空間中等 |
| Rest | 1.0 | 冇口型限制,情緒可以完全表現 |

**混合公式套用示範**(開心 0.6 強度 + 口型 O):
```
finalMouthOpen = viseme.mouthOpen(O) = 0.5   // 口型主導,唔受情緒改變
finalMouthWidth = viseme.mouthWidth(O) + emotionWeight(O) × 0.6 × (emotion.mouthWidth(happy) − neutral.mouthWidth)
                = 0.75 + 0.5 × 0.6 × (1.35 − 1.0)
                = 0.75 + 0.105 = 0.855
finalCornerL/R = neutral.corner + emotionWeight(O) × 0.6 × (emotion.corner(happy) − neutral.corner)
```

### 3.3 進階概念:JALI 模型——下顎(Jaw)同嘴唇(Lip)分開控制
一個更加精細嘅業界做法(JALI 模型)提出咗更根本嘅拆解:<cite index="65-1">聲音主要由下顎動作同下半臉肌肉分別控制,呢個對應緊語音學研究——聲音訊號入面嘅聲學特性,可以自然噉映射去「下顎」同「嘴唇」呢兩個獨立視覺維度嘅動態程度。</cite>

**對你套系統嘅長遠建議**:目前你嘅 mouthOpen 其實混合咗「下顎張開」同「嘴唇張開」兩件事。如果想做到更專業級嘅口型精度,可以將 mouthOpen 拆做兩個獨立參數:
- `jawOpen`:對應聲音響亮度/開口幅度(主要受口型嘅「A/O」類音素驅動)
- `lipCompression`:對應嘴唇本身嘅收緊/放鬆(主要受「M/B/P/F/V」類音素驅動)

呢個拆分而家可以留做未來擴充,現階段用單一 mouthOpen 近似都已經足夠做到可信嘅第一版。

## Part 4:整合返 Layer 架構

```
Layer 0 · 劇本(text 對白)
    ↓ [新增] 文字轉音素轉口型(Text → Phoneme → Viseme)
Layer V · 口型序列 (Viseme Sequence)
    ↓ 同 Layer 1(情緒強度值)一齊輸入
Layer 1+V 混合器 (Emotion-Viseme Blender)
    ├─ 上半臉:100% 情緒主導
    └─ 下半臉:口型主導開合/寬度 + emotionWeight 加權嘅情緒疊加(嘴角/微調)
    ↓
Layer 2 · 臉部點位值(最終輸出)
```

**簡化版文字轉口型邏輯**(俾第一版 prototype 用,唔使做到完整語音學分析):
- 母音 a/e/i/o/u → 對應 AI/E/AI/O/U 口型(i 暫時歸類做 AI 嘅窄版本)
- 常見閉口輔音 m/b/p → MBP
- f/v → FV
- l → L
- 其他輔音 → 一般輔音口型
- 空格/標點 → 短暫 Rest

呢個只係一個「近似示範」,真正產品化需要正式嘅文字轉音素(text-to-phoneme)工具或者
TTS 系統自帶嘅音素時間戳(大部分現代 TTS API 都可以輸出呢個)。
