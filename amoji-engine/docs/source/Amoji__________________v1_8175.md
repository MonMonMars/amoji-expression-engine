# Amoji 系統規格 —— Part PP:「純生成引擎」定位嘅落實清單

呢份文件將上次歐盟法規研究揭示嘅「生成 vs 偵測」區分,轉化做具體要做嘅嘢——分三層:
架構層、合約層、文件層。三層都做齊,先算真正落實咗呢個定位,唔係得個講字。

---

## 層一:架構層——確保引擎結構上冇能力做「偵測」

### 1.1 輸入合約(Input Contract)必須係「抽象語意」,唔可以係「原始生物特徵」
呢個係最核心嘅原則:

```
容許嘅輸入(Layer 0 劇本):
  { emotion: "sad", intensity: 0.6, mood: "embarrassed" }
  —— 呢啲係已經被上游AI/劇本決定好嘅抽象標籤,Amoji淨係負責將標籤轉做表情

唔容許嘅輸入:
  用戶鏡頭畫面、用戶聲音原始波形、用戶心跳/皮膚電阻等生物感測數據
  —— 一旦 Amoji 引擎本身接收呢類數據並且從中推斷用戶情緒,就已經跨咗去「偵測」
```

**實作要求**:Amoji 嘅 SDK/API 文件,應該喺輸入參數規格度明文寫低——「本引擎唔接受、
唔處理任何用戶生物特徵原始數據」,呢個唔止係政策聲明,而係實際上 API 根本冇對應嘅
輸入欄位。

### 1.2 需要重新設計/移除嘅功能——「瞳孔同步」「情緒鏡像」
之前文件23(對話與演講眼神模式)提過嘅「對話對象情緒高峰時,Amoji同步調整自己瞳孔
放大幅度」——呢個功能如果要偵測用戶真實情緒先做到,就會跨界。

**兩個解決方向,揀一個**:
1. **移除呢個功能**,最簡單、風險最低
2. **重新設計做「劇本驅動」版本**:唔係 Amoji 自己讀用戶鏡頭/聲音去判斷用戶情緒,而係
由上游host application/LLM(呢個先可能涉及情緒分析,同 Amoji 引擎本身分開)分析
用戶輸入嘅文字內容(唔係生物特徵),然後將結果做成一個抽象標籤(例如
`user_mood_hint: "moved"`)傳落嚟 Layer 0 劇本——Amoji 淨係反應呢個文字標籤,自己
從來冇接觸過用戶嘅樣、聲、心跳呢類原始生物數據

**建議採用方向2**,因為呢個保留咗功能嘅價值(對話更有溫度),同時將「分析用戶」呢個
責任明確留俾 host application,Amoji 本身保持乾淨。

### 1.3 技術自我檢查清單(Claude Code 實作時逐項核對)
```
□ Layer 0 輸入 schema 入面,完全冇任何「鏡頭」「麥克風原始音頻」「生物感測器」類欄位
□ Layer E(眼球錨點)嘅「錨點」概念,錨點座標由劇本/場景設定提供,唔係由分析用戶
  面部/眼神推斷出嚟
□ 心情引擎(Layer -1)嘅輸入,全部係文字/標籤形式,冇圖像/音頻原始數據處理模組
□ 如果將來要加「觀察者模式」(Amoji角色需要判斷緊對話對象嘅情緒),必須做成完全
  獨立、清楚標籤做「情緒偵測模組」嘅組件,唔可以掛喺表情生成引擎入面
```

## 層二:合約層——防止 B2B 客戶將 Amoji 改裝做偵測工具

### 2.1 標準合約條款(建議寫入所有授權/SDK合約)
- 客戶唔可以將 Amoji 引擎輸出結果,回頭用嚟訓練或者建構「偵測用戶情緒」嘅系統
- 客戶如果自行加裝攝影機/麥克風做用戶情緒分析,必須喺自己嘅系統文件明確標示呢個
係「客戶自建嘅偵測模組」,唔可以聲稱係「Amoji嘅功能」——保護 Amoji 品牌唔被
連累落客戶自己加嘅偵測功能

### 2.2 對之前接觸目標(AheadForm/UBTech/Realbotix)嘅實際意義
呢三間公司嘅硬件本身已經有鏡頭/麥克風做用戶互動感知(例如 Realbotix 嘅「感知AI
整合」)——授權合作嗰陣,必須清楚喺合約入面劃分:邊部分係佢哋自己嘅感知/偵測層
(佢哋負責、佢哋承擔合規責任),邊部分係 Amoji 提供嘅純表情生成層(你哋負責、你哋
嘅合規責任範圍僅限於呢部分)。

## 層三:文件層——對外聲明同行銷語言

### 3.1 建議加入 pitch one-pager 嘅新賣點段落
「Amoji 係一套純表情生成引擎——我哋唔分析、唔偵測、唔儲存用戶嘅樣貌、聲音、或者任何
生物特徵數據。所有情緒輸出,都源自劇本層面嘅語意指令,而唔係對用戶嘅生物特徵推斷。
呢個設計令 Amoji 天然回避咗歐盟AI法案第5(1)(f)條(職場/教育場景生物特徵情緒偵測
禁令)嘅適用範圍,亦都令客戶嘅隱私合規負擔大幅降低。」

**呢個唔止係合規保護,仲係一個具體、可以量化嘅銷售論述**——「我哋幫你減輕隱私合規
負擔」對機械人/AI平台客戶嚟講,係一個實在嘅價值,唔係得個講字。
