## Part 1:呢個模式已經有成功先例——「Open Core」

<cite index="22-1">開源做企業服務:提供付費支援、整合、諮詢服務,呢個係好多資料庫/開發工具公司
嘅做法——保留核心開源產品免費,但進階外掛/擴展規模功能收費。</cite><cite index="22-1">
開源可以幫你喺市場建立事實標準——如果你嘅開源軟件成為業界標準,你自然攞到
最大嘅市場話語權。</cite>

### 1.1 真實案例對照
<cite index="25-1">GitLab:核心功能(原始碼管理、基礎議題追蹤)開源免費,靠Premium/Ultimate
付費方案同訂閱附加功能變現。</cite><cite index="23-1">GitLab、Elastic、MySQL都用開源
核心模式,提供免費工具,靠進階功能/支援收費——開源軟件市場由2017年110億美元
增長到2022年330億美元,預計2026年達500億美元。</cite>

呢個模式對你哋嘅吸引力:如果 Amoji 嘅「情緒生成協議」(即係 Layer 1 輸出
格式、情緒分類、強度量表)成為業界事實標準,你哋就會攞到定義業界規則嘅話語權
——所有後來者(其他機械人/AI公司)都要用返你哋定義嘅格式,呢個先真正做到你哋
想要嘅「Amoji成為業界統一情緒系統」。

## Part 2:一個必須知道嘅風險——4間公司連續中招嘅教訓

### 2.1 MongoDB、Elastic、HashiCorp、Redis 嘅共同命運
<cite index="32-1">呢個模式喺2018至2026年重複出現:MongoDB(2018)、Elastic(2021)、
HashiCorp(2023)、Redis(2024)。MongoDB 2018年由AGPL改做SSPL牌照,原因係
AWS推出「DocumentDB」——一個相容MongoDB嘅代管服務,但完全冇貢獻返code或者
收入俾MongoDB。</cite>

<cite index="34-1">MongoDB嘅意圖好清晰:「如果你將我哋嘅資料庫做成服務銷售,你要
嘛將你成套服務基建都開源,要嘛畀錢俾我哋。」AWS建咗自己嘅DocumentDB,MongoDB
保護咗自己,但永遠失去咗AWS呢個用戶。</cite>

### 2.2 呢個模式對 Amoji 嘅直接對應風險
如果你哋將「情緒協議」做到完全開源(連參考實現嘅代碼都公開,用寬鬆牌照如
MIT/Apache 2.0),一個具規模嘅大型雲端商/AI巨頭(例如Google、Microsoft、
或者中國大廠)完全可以攞你哋嘅開源代碼,自己包裝做付費服務,你哋一分錢都
攞唔到——呢個正正就係AWS對MongoDB/Elastic做過嘅事。

<cite index="31-1">評論精準總結咗呢個模式失敗嘅根本原因:呢啲公司建立嘅商業模式
本質好簡單——免費派軟件,然後圍住佢賣服務(企業支援、代管、安全功能、諮詢)。
呢個模式運作良好,前提係假設「呢間公司會一直係嗰啲付費服務嘅主要提供者」——
冇人預計到接下嚟發生嘅事。</cite>

## Part 3:解決方案——分清楚「協議」同「引擎」兩件唔同嘅嘢

### 3.1 核心策略建議:協議開放,引擎唔開源
呢個係最重要嘅一條建議,可以避開MongoDB/Elastic嘅陷阱:

```
建議開放(做成公開規格文件,唔係開源代碼):
   - Layer 1 輸出格式定義(JSON schema:emotion、intensity、valence、arousal等欄位)
   - 情緒分類命名標準(8基礎情緒+複合情緒嘅命名慣例)
   - Layer CA 角色原型嘅介面定義(available channels嘅抽象概念)
   - 類似 ARKit 52 blendshapes 咁,做一份「業界都可以參考嘅命名標準」

唔建議開源(保留做付費產品嘅核心價值):
   - 實際嘅情緒公式/數值(肌肉幅度矩陣)
   - 心情引擎、複合情緒區域分工嘅具體演算法
   - 全套規則庫嘅參考實現(reference implementation)
```

呢個做法嘅精妙之處:一份「規格文件」(好似HTTP、MIDI呢類協議),冇代碼可以
俾雲端商攞去代管服務——你冇「服務」可以俾人白食,因為協議本身唔係一個可以
部署嘅產品,只係一份大家都跟嘅共同語言。真正嘅產品(高質素、心理學根據嘅實現)
先至係你哋嘅收費項目,而呢個先至保留晒你哋嘅IP價值。

### 3.2 精確類比:ARKit 52 Blendshapes 嘅商業模式
之前已經研究過——ARKit 52 blendshapes 已經係「事實業界標準」,但呢個標準本身
冇令蘋果損失收入:蘋果控制緊硬件(TrueDepth鏡頭)同官方SDK,標準只係令更多
開發者願意投入呢個生態,而唔會削弱蘋果嘅商業利益。你哋可以複製呢個邏輯——
「Amoji 情緒協議」開放,但「攞到心理學/解剖學根據嘅高質素實現」呢件事,先至
係你哋嘅「TrueDepth鏡頭」(核心技術優勢),協議本身推唔跌你哋。

### 3.3 免費基礎版嘅具體設計建議
```
免費開源層(建立生態/採用率):
  - 8個基礎情緒(冇複合情緒)
  - 冇心情引擎(每次都由中性起始,冇長期記憶偏壓)
  - 冇合規三機制(AI披露/防沉迷/危機介入——呢個反而可以做付費層嘅賣點,
    因為呢個係企業客戶最在意嘅合規保障)
  - 冇Layer CA擴充原型(淨係人類基礎版)
  - 牌照建議:如果要開源代碼,建議用類似 Elastic License / SSPL 呢種
    「來源可見但限制雲端代管服務」嘅牌照,唔好用純MIT/Apache

付費進階層(你哋嘅實際商業產品):
  - 複合情緒引擎、心情引擎
  - 合規三機制(呢個對B2B客戶嚟講,價值遠超技術功能本身)
  - Layer CA全部原型(動物/物件/機械人)
  - 恐怖谷風險評估支援、跨越恐怖谷清單覆核服務
  - 十級Surface Renderer全套
```

## Part 4:定位論述——點樣講呢個故事

建議嘅品牌敘事:「Amoji 情緒協議(Amoji Emotion Protocol,簡稱AEP)係一套
開放、免費嘅AI情緒表達標準格式,任何開發者都可以用嚟令自己嘅AI角色/機械人
講得出情緒語言。Amoji 引擎係業界第一個、亦都係心理學根據最紮實嘅參考實現——
你可以自己實現AEP協議,或者直接用Amoji引擎攞到即用即有嘅高質素效果。」

呢個論述嘅巧妙之處:協議本身唔係你哋嘅收費項目(所以推廣協議唔會削弱你哋
收入),你哋收費嘅係「最好嘅實現」——同開源社群嘅慣常做法(業界標準推廣者
本身唔一定係最大得益者)相反,你哋反而利用「制定標準」呢件事,加強咗「Amoji
先係最權威實現」呢個市場定位。
