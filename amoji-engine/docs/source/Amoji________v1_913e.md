# Amoji —— 開源牌照比較(俾 Amoji 引擎參考實現用)

⚠️ 免責聲明:我唔係律師,以下係基於同業案例嘅事實整理,實際採用嘅牌照文本
必須搵有開源商業經驗嘅律師審閱/客製。

呢份文件淨係討論如果你哋決定將部分引擎代碼開源(唔止協議文件)嗰陣,揀
邊種牌照——如果你哋跟返上次建議,協議純粹做文件唔做代碼,呢份文件屬於「以防
萬一」嘅參考。

## Part 1:四個選項嘅具體限制對比

| 牌照 | 核心限制 | OSI認可開源? | 代表案例 |
|---|---|---|---|
| MIT / Apache 2.0 | 冇任何限制,可以自由商用/代管服務 | 是 | 大部分npm套件 |
| Elastic License 2.0 (ELv2) | 禁止用嚟提供「競爭性代管服務」,其餘(使用/複製/發佈/修改)都容許 | 否(source-available) | Elasticsearch/Kibana(2021年起) |
| SSPL | 容許使用/修改/重新發佈,但如果你用嚟對外提供服務,你必須將你成套服務管理層(包括你自己嘅基建代碼)都公開,而唔止係本身嘅軟件 | 否,曾提交OSI審批但因為爭議太大而撤回 | MongoDB |
| BSL/BUSL | 代碼可以喺非生產環境自由閱讀/使用,但商業生產環境使用需要另外授權,直到指定日期(通常4年)後自動轉為完全開源牌照 | 否 | HashiCorp Terraform、CockroachDB |

## Part 2:每個選項對 Amoji 嘅實際適用性評估

### 2.1 MIT/Apache 2.0——唔建議
MIT係最廣泛使用嘅開源牌照,授予任何人使用/複製/修改/合併/發佈/發行/再授權/
銷售嘅權利,唯一要求係保留原始版權聲明。呢個正正係MongoDB/Elastic最初用嘅
牌照,亦都係佢哋出事嘅根源——冇任何限制代管服務,大型雲端商可以直接攞嚟做
付費服務,Amoji一分錢都攞唔到。唔建議用喺任何你哋想保留商業價值嘅代碼上面。

### 2.2 Elastic License 2.0——相對適合初創嘅選項
Elv2 嘅限制簡單、明確、容易理解:唔可以將軟件包裝做競爭性代管服務,除此
之外幾乎乜都容許(自用、修改、再發佈、商用產品內嵌)。如果你用返官方發佈嘅
預設版本,對你嚟講其實冇分別,一切如常。

建議:如果 Amoji 決定開源基礎版引擎代碼,Elv2 係最平衡嘅選項——夠寬鬆
吸引開發者採用,但守住咗「大廠攞去代管服務賺錢」呢條底線。

### 2.3 SSPL——過於進取,唔建議初創階段用
SSPL 嘅要求(如果對外提供服務,連你自己嘅服務管理基建都要公開)遠超一般
開發者/中小企嘅接受程度。「競爭性提供」「生產環境使用」呢類用詞會製造法律
灰色地帶——搞錯咗可能引致昂貴嘅授權談判,或者被迫遷移走你成套產品建立喺
上面嘅依賴。對於一間仲喺概念驗證階段、想盡量吸引開發者/合作夥伴嘅公司嚟講,
SSPL 嘅「嚇怕人」風險大過保護作用。

### 2.4 BSL/BUSL——一個有趣嘅中間路線,值得考慮
呢個牌照可以講一個特別吸引人嘅故事:「而家用免費、幾年後轉做完全開源」——
呢個承諾本身有助建立開發者信任(對比 MongoDB/Elastic 咁「突然轉軚」引發社群
反彈)。代碼可以喺非生產環境自由閱讀使用,生產環境商業使用需要授權,通常4年
後自動轉做完全開源牌照。

對 Amoji 嘅意義:如果你哋想講一個「我哋由第一日就承諾終將完全開源」嘅故事
(比 Elv2 更加「開放友善」嘅形象),BSL 係一個值得考慮嘅選項——尤其係你哋
「協議開放、引擎最終都會開放」呢個長遠敘事,同 BSL 嘅時間延遲開源機制天然吻合。

## Part 3:社群信任嘅教訓——牌照改變本身有代價
科技評論界對呢類牌照轉換嘅反應普遍負面:「如果你信任Elastic講嘅任何保證,
你係傻仔,應該做定其他打算。」

對你哋嘅意義:呢個教訓最重要嘅啟示唔係「揀邊種牌照」,而係——你哋應該由
第一日就揀啱牌照,而唔係好似MongoDB/Elastic咁,一開始用寬鬆牌照吸引用戶,
之後先「臨時轉軚」。臨時轉軚會摧毀你哋辛苦建立嘅開發者信任,你哋而家仲喺
起步階段,冇呢個「先甜後苦」嘅歷史包袱,應該由一開始就揀返適合你哋長遠商業
模式嘅牌照。

## Part 4:最終建議(綜合)

```
首選:協議(AEP規格文件)用 CC-BY 4.0,唔涉及代碼,完全冇代管服務風險

如果都想開源部分引擎代碼(建立生態/示範用途):
  建議:Elastic License 2.0
  理由:限制單一、清晰(唔可以做競爭代管服務),對開發者友善,
        業界已有大量先例、社群理解呢類牌照嘅意涵

如果想講「終將完全開放」嘅長遠故事:
  考慮:BSL/BUSL(例如4年後自動轉做MIT/Apache)
  理由:建立長遠信任,同「協議開放」呢個核心敘事一致

避免:
  - 純MIT/Apache(俾大廠白食嘅風險太大)
  - SSPL(對初創嚟講太進取,可能嚇怕潛在合作夥伴)
```
